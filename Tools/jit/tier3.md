# Tier-3 integer-loop experiment

## Existing architecture (milestone 0)

The trace is an array of `_PyUOpInstruction` owned by an executor
(`pycore_uop.h` and `pycore_optimizer.h`).  `optimizer_analysis.c` performs
abstract interpretation and removes redundant uops.  `optimizer.c` then uses
the generated stack-cache tables as its register allocator.  The current JIT
maps every remaining uop to a generated stencil in `Python/jit.c`, allocates a
single code/data mapping, patches exits and symbols, and publishes it through
`jit_publish.c`.  Side exits retain an executor and resume at their bytecode
target.  Executors expose their uops and generated bytes through `_opcode`;
`sys._dump_tracelets()` provides the existing graph dump.

## Prototype boundary

The prototype deliberately sits beside, rather than inside, the current JIT.
It accepts the executor sequence exposed by `_opcode.get_executor()`, rejects
unsupported traces, lowers one exact shape (`range` integer reductions) to a
small value IR, and emits a System V x86-64 leaf function.  The Python adapter
performs an exact-`int` guard and bounds checks at entry.  Guard failure,
unsupported traces, non-Linux platforms, and arithmetic that may overflow
signed 64-bit all call the unchanged Python function.  Consequently arbitrary
precision integers, `bool`, and subclasses retain normal Python behavior.

There are no Python objects, iterator operations, dispatches, reference-count
updates, or helper calls in the native loop.  Only the final `ctypes` return is
boxed.  This is not yet wired to executor side exits, so it is an experiment,
not a production runtime implementation.

## Generated code

With `PYTHON_TIER3_DUMP=1`, the benchmark writes `.ir` and `.bin` files.  Inspect
the latter with:

```sh
objdump -D -b binary -m i386:x86-64 sum_range.tier3.bin
```

The 26-byte `sum_range` body is:

```asm
xor %rax, %rax
xor %rcx, %rcx
test %rdi, %rdi
jle exit
loop: add %rax, %rcx
inc %rax
cmp %rax, %rdi
jg loop
exit: mov %rcx, %rax
ret
```

`sum_squares` adds only `mov` and `imul`, and is 33 bytes.

## Measurement

Run an optimized JIT-enabled build using:

```sh
./python Tools/jit/tier3_bench.py > tier3-results.json
```

The parent launches fresh baseline (`PYTHON_JIT=0`), current-JIT
(`PYTHON_JIT=1`), and Tier-3 (`PYTHON_JIT=1 PYTHON_TIER3_JIT=1`) processes.
Each child warms the function before locating its executor, reports compilation
separately, takes nine steady-state samples by default, and reports medians and
speedups.  A Tier-3 row is valid only when `compiled` is true; otherwise the
row explicitly represents fallback.  CPU pinning and `perf stat` should be
performed externally because policy differs by test host.

A sample result and its limitations are recorded in `tier3_results.md`; the JSON
output remains the authoritative artifact for each experiment host.
